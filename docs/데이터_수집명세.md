# 협력사 품질 리스크 — 데이터 수집 명세

작성 2026-09-07 · **09-07 실무조사 반영**(`품질검사_실무조사.md`). 대상은 **F4GE가 협력 공장에 요구할 보고 항목**과 **F4GE가 스스로 기록해야 할 항목**이다.
합성 생성기의 관측 필드와 1:1로 대응한다 — 여기 없는 필드는 생성기에도 없고, 모델도 쓰지 않는다.

---

## 0-0. 출처는 네 곳이다 (2026-09-08 저녁 확정 — 사용자)

FactoryOS 에는 **MES · CellOS · ERP · 포지 기록** 네 소스가 **12곳 전부**에서 들어온다. 연동/미연동 유형 구분은 폐기했다.
공장마다 다른 것은 **보고 품질** 4축이다 — 값의 정직도(편향) · 기입 성실도(누락·지연·빈칸) · 채우는 필드 · 형식(주기·단위·불량코드).

| 소스 | 계약 | 층 | 무엇 | 성질 |
| --- | --- | --- | --- | --- |
| 포지 기록 | `supplier-order.v1` · `order-quality-outcome.v1` | L0 · 라벨 | 발주·견적·단가·납기 변경·질의 응답 시각 · **입고검사 결과·클레임(y)** | 우리 것. 조작 불가 |
| MES | `factory-report.v1` | L1 | 생산·폐기·재작업·자체검사·공정 단계·특이사항 | 자기신고. **편향이 걸린다.** 주기 일/시프트/주, 단위 개/로트, 코드 표준/자체 |
| CellOS | `cell-daily.v1` | L2 | 가동률·사이클·이상 이벤트·**카운터(실제 생산)** | 설비 값. 편향 없음 |
| ERP | `erp-daily.v1` | L3 | 자재 입출고·재고 · 재공/공정별 재고 · 인원·잔업 · 외주 발주/입고 | 회계 값. 편향 작음. **MES 의 대조군** |

이 조합이 모델 목표 둘을 가능하게 한다(사용자, 09-08 저녁): ERP 자재 소진 − Cell 카운터 = **물리적 폐기**.
그것을 MES 보고와 대조하면 **보고 정직도**, 우리 입고검사와 대조하면 **검수 품질(검출률)**, 둘을 합치면 **제조 품질(내부 불량률)**이 나온다 → `models/factory_params.py`.

> 아래 §1~§7 은 09-08 오전의 T1/T2/T3(요구 단계) 서술이다. 네 소스가 전부 온다는 전제에서는 "무엇을 요구하나"가 아니라
> "무엇이 오고 어디가 비는가"의 문제가 된다. 항목 정의는 유효하고, 유형 a/b 언급은 무효다.

## 0. 설계 원칙 다섯

1. **공장은 바쁘다.** 담당자 1명이 카톡·엑셀로 일한다. T1(필수)은 **5분 안에 입력 가능**해야 한다.
   항목이 많으면 보고가 형해화되고, 형해화된 보고는 노이즈가 아니라 **거짓 신호**다.
2. **조작 난이도로 항목을 등급화한다.** 공장이 평가받는다는 걸 아는 순간 자기평가는 오염된다.
   `자기평가 < 수량 < 타임스탬프·사진 < 자동수집` 순으로 신뢰한다.
3. **같은 사실을 두 경로로 받는다.** 교차검증 쌍(§3)이 이 모델의 핵심 상품인
   **불일치 탐지**를 가능하게 한다. 한 경로로만 받으면 검증할 방법이 없다.
4. **메타데이터가 본문만큼 중요하다.** 언제 보냈는가, 얼마나 늦었는가, 뭘 빠뜨렸는가는
   공장이 조작하기 어렵고(늦게 보내면 늦은 게 남는다) 예측력이 높을 가능성이 크다.
   그리고 **이건 공장에 요구할 필요조차 없다** — 우리가 자동으로 남긴다.
5. **처음부터 다 요구하지 않는다.** T1은 계약에 넣고, T2는 교섭하고, T3는 CellOS 설치의 대가로 얻는다.

## 1. T1 — 필수 (계약에 명시, **FactoryOS 가 공장 MES/ERP API 에서 일 1회 수집**)

⚠ **2026-09-08 변경.** T1 은 사람이 채우는 주간 양식이 아니라 **MES API 의 일 단위 집계**다
(→ `프로젝트_정리.md` §5-1). 따라서 계약에 넣을 것은 「양식 제출 의무」가 아니라 **API 연동**이다.
공장 유형에 따라 오는 것이 다르다 — **자체 MES 를 FactoryOS 에 연동한 유형 a(3곳)만 T1 이 온다.** 나머지 9곳(b)은 설비 신호만 온다(CellOS·FactoryOS 는 12곳 전부 설치).
아래 항목 자체는 그대로다. 오는 경로와 주기가 바뀐 것이다.

| # | 필드 | 형식 | 왜 필요한가 |
| --- | --- | --- | --- |
| 1 | `reported_at` | 일시 (자동) | 지연·누락 계산의 기준. 공장이 입력하지 않는다 |
| 2 | `produced_qty` | 정수, 누적 | 진척률. 추세 외삽으로 완료일 추정 |
| 3 | `scrap_qty` | 정수, 누적 | **폐기와 재작업을 반드시 분리한다.** 합쳐 받으면 불량 은폐가 보이지 않는다 |
| 4 | `rework_qty` | 정수, 누적 | 〃 |
| 5 | `stage` | enum: `setup` / `machining` / `finishing` / `inspection` / `packing` | 진척률과 교차검증. 수량은 늘었는데 단계가 그대로면 이상 |
| 6 | `promised_date` | 날짜 | **매 보고마다 다시 받는다.** 값 자체보다 **변동 이력**이 신호다 |
| 7 | `issue` | 있음/없음 + 한 줄 | "없음"이 반복되다 갑자기 "있음"이 되는 시점, 그리고 "없음"인데 보고가 늦는 조합 |

> **미보고도 데이터다.** 계약에 "미보고 시 리스크 점수에 반영된다"를 명시해야 T1이 실효를 갖는다.
> 벌칙이 아니라 **결측을 신호로 쓴다는 선언**이다.
> ⚠ 09-08 이후 결측의 의미가 바뀌었다 — **사람의 누락이 아니라 API 끊김**이다.
> 다만 `scrap_qty` / `rework_qty` 의 **폐기·재작업 판정은 여전히 사람이 하므로 편향은 남는다.**

## 2. T2 — 교섭 대상 (값이 크다)

T1보다 얻기 어렵지만 **모델 성능의 대부분이 여기서 나온다.** 오더 단가 협상이나
CellOS 도입 논의에 끼워 넣을 항목들.

### 2.1 검사 문서 — 가장 값이 크다

> ⚠ **COC를 받으면 안 된다.** COC(Certificate of Conformance)는 공장 자체 선언이고
> **측정값이 한 개도 없다.** "품질검사서 주세요"라고 하면 COC가 온다.
> 계약 문구를 **"측정값이 포함된 출하검사성적서(Inspection Report)"**로 정확히 박아야 한다.
> 근거: `품질검사_실무조사.md` §2

**(a) 초도품 검사(FAI) — T2 최우선**

오더 시작 직후 첫 물건에 대한 **전 치수 실측 리포트**. **진행률 10% 시점에 얻을 수 있는
유일한 상세 품질 정보**다.

| 필드 | 비고 |
| --- | --- |
| `fai_at` | 초도품 검사 일시 |
| `fai_dimensions[]` | 항목별 `{규격, 공차상하한, 실측값}` |
| `fai_margin_min` | **공차 여유의 최솟값** — 첫 물건부터 아슬아슬하면 공구가 마모될수록 넘어간다 |

합/불이 아니라 **연속값**이라 정보량이 훨씬 크다.

**(b) 공정검사 — 초·중·종물, 자주검사**

**공장이 이미 만들고 있는 기록이다.** 4M 변동으로 불량이 대량 발생하기 전에 잡는 목적의
한국 제조업 표준 관행이라, 새로 만들라는 요구가 아니라 **있는 걸 달라는 요구**다.
협상 난이도가 T2 중 가장 낮다.

| 필드 | 비고 |
| --- | --- |
| `inproc_checked_at` | 초물 / 중물 / 종물 구분 |
| `inproc_result` | 합/불 + 측정값 |
| `inproc_action` | 이상 시 조치 내용 |

**(c) 출하검사 결과**

| 필드 | 형식 | 비고 |
| --- | --- | --- |
| `inspected_qty` | 정수 | |
| `inspection_type` | `full` / `sampling` | 표본이면 **표본 크기 필수** — y 가중치에 쓴다 |
| `reject_qty` | 정수 | |
| `defect_type` | enum | **표준 코드 필수** — 아래 |

**불량 유형 코드를 우리가 정해서 내려보내야 한다.** 자유 서술로 쓰면 집계가 안 된다.
최소 5종: `dimension`(치수) / `surface`(외관·거칠기) / `function`(기능·조립) /
`material`(소재 결함) / `other`. 유형별로 원인 계층이 다르다 — 치수는 공구·설비,
외관은 가공 조건, 소재는 자재 로트.

### 2.2 자재

| 필드 | 왜 |
| --- | --- |
| `material_lot_id` | 같은 자재 로트를 쓴 오더들이 함께 나빠지는 패턴. **공장 간 전파도 잡힌다** — 같은 공급사를 쓰는 두 공장이 동시에 나빠지면 공장 문제가 아니다 |
| `material_supplier` | 〃 |
| `material_received_at` | 자재 지연 → 서두름 → 불량의 인과 경로 |
| `material_mtc` | 소재 시험성적서(Mill Sheet / EN 10204 3.1). 로트·성분·기계적 성질. 자재 로트 추적의 근거 |
| `material_consumed_qty` | **`produced_qty`의 교차검증 대조군**(§3) |

### 2.3 작업 조건

| 필드 | 왜 |
| --- | --- |
| `machine_id` | 어느 설비에서 났는지. 공장 전체가 아니라 설비 1대 문제일 수 있다 |
| `shift` | 야간조 품질 저하는 현장의 고전적 패턴 |
| `operator_count` | 인력 이탈이 잠재변수. 직접 물으면 답 안 하지만 인원수는 답한다 |
| `overtime_hours` | **서두름의 직접 관측치.** 납기 압박 → 잔업 → 불량 |

### 2.4 사진

공정 중 1장 + 검사 중 1장. **EXIF 타임스탬프가 검증 수단이다**(§3). 사진 자체를 모델이 보는 건
나중 일이고, 지금 값은 "그 시각에 실제로 그 작업을 하고 있었다"는 증거다.

## 3. 교차검증 쌍 — 이 문서의 핵심

**같은 사실을 두 경로로 받아 어긋남을 본다.** 불일치가 곧 전화·방문 트리거다.

| 보고 A | 대조 B | 어긋나면 |
| --- | --- | --- |
| `produced_qty` | `material_consumed_qty` | **수량 부풀리기.** 자재는 안 줄었는데 생산은 늘었다 |
| `produced_qty` | (T3) 설비 가동시간 × 사이클타임 | 〃 |
| `reject_qty` | `rework_qty`, `overtime_hours` | **불량 은폐.** 불량은 없다는데 재작업과 잔업이 늘어난다 |
| `promised_date` | `produced_qty` 추세 외삽 | **낙관 보고.** 지금 속도로는 절대 못 맞추는 날짜를 계속 말한다 |
| `issue` = "없음" | 보고 지연·응답 지연 | **문제 은폐.** 곤란한 공장은 연락이 느려진다 |
| 사진 EXIF 시각 | `reported_at` | **과거 사진 재사용.** 지난주 사진을 다시 보냈다 |
| `stage` | `produced_qty` 변화 | 단계는 검사인데 수량이 계속 늘어난다 = 양식만 채웠다 |

각 쌍에서 **`gap` 지표**를 만들고, 오더 단위로 합산한 `discrepancy_score`가 관리자 화면의
두 번째 숫자가 된다(첫 번째는 예측 불합격률).

## 4. L0′ — 우리가 자동으로 남기는 것 (공장 협조 불필요)

**요구할 필요가 없고, 조작이 불가능하고, 오늘부터 기록 가능하다.** 우선순위가 가장 높다.

| 필드 | 산출 방법 |
| --- | --- |
| `report_delay_days` | 예정 보고일 대비 실제 도착 |
| `report_missing_count` | 누락 회차 수 |
| `field_blank_count` | 보고서에서 비워 보낸 항목 수 |
| `response_latency_h` | 우리가 물어본 시각 → 답이 온 시각 |
| `promised_date_change_count` | 납기 변경 횟수 |
| `promised_date_change_at` | 변경 시점 (진행 후반의 변경이 훨씬 나쁜 신호) |
| `quote_response_h` | 견적 요청 → 회신 시간 |
| `quote_price_zscore` | 같은 품목 견적 대비 단가. **비정상적으로 싸면 위험** |
| `order_lead_slack` | (약속 납기 − 표준 소요일) / 표준 소요일. 음수면 애초에 무리한 일정 |

> ⚠ **이 중 셋은 지나가면 복원 불가능하다** — `reported_at`, `response_latency_h`,
> `promised_date_change_at`. 결과값은 나중에 소급 정리가 되지만 시각은 사라진다.
> 지금부터 오더별로 한 줄씩 남기기 시작해야 한다.

## 5. 라벨 — F4GE가 기록해야 할 정답값

**이게 y다.** 공장 협조가 필요 없고, 우리가 기록을 안 하면 이 프로젝트 자체가 성립하지 않는다.

### 5.1 라벨은 네 번에 걸쳐 도착한다

단일 시점이 아니다. 조사 결과가 이걸 뒤집었다(`품질검사_실무조사.md` §5).

| 라벨 | 지연 | 신뢰도 | 쓰임 |
| --- | --- | --- | --- |
| **공장 자체 출하검사** | **0** | 낮음 (자기 채점) | 빠른 갱신용. 편향 보정 필요 |
| **PSI (제3자 선적전검사)** | 0 | **높음** | 우리가 발주하면 생긴다 |
| **우리/고객 입고검사** | **美서안 18 · 美동안 30 · 유럽 60일** | 높음 | **주 타깃** |
| **고객 클레임** | 수개월 | 최고 | 희소사건. 비용 가중치 쪽 |

→ **다중 라벨로 학습한다.** 빠르고 약한 라벨로 자주 갱신하고, 느리고 강한 라벨로 보정한다.
하나만 기다리면 학습이 몇 달에 한 번 돈다.

→ **클레임을 주 타깃으로 삼지 않는다.** 너무 드물어서 학습이 안 된다.

### 5.2 y를 2층으로 정의한다

입고검사는 전수가 아니라 **AQL 표본검사**다(ISO 2859-1). 그래서:

| | 정의 | 성질 |
| --- | --- | --- |
| `y_lot` | 로트 **합격/불합격** | 계약상 결정. 깨끗하지만 정보량 적음 |
| `y_rate` | 표본 불량수 / **표본 수** | 정보량 크지만 표본 크기에 따라 노이즈가 다르다 |

⚠ **`y_rate`는 표본 크기를 가중치로 넣어야 한다**(이항 관측). 표본 50개짜리와 200개짜리를
같은 신뢰도로 학습하면 소량 오더가 모델을 흔든다.

⚠ **합격 ≠ 불량률이 AQL 이하.** AQL은 여러 로트에 걸친 평균적 보증이지 그 로트의 보증이 아니다.

### 5.3 기록 필드

| 필드 | 형식 | 비고 |
| --- | --- | --- |
| `shipped_at`, `arrived_at` | 일시 | 라벨 지연을 재는 값 |
| `incoming_inspected_qty` | 정수 | **표본 크기.** y 가중치 |
| `incoming_inspection_type` | `full` / `sampling` | |
| `incoming_reject_qty` | 정수 | `y_rate` = reject / inspected |
| `incoming_lot_result` | `accept` / `reject` | `y_lot` |
| `incoming_defect_type` | §2.1 코드와 동일 | |
| `aql_class` | critical / major / minor 별 AQL 값 | 계약 합격기준. 관행: 0 / 2.5% / 4.0% |
| `claim_occurred`, `claim_at`, `claim_qty`, `claim_cost` | | 희소·고비용 |
| `ncr_issued`, `scar_response_h` | | **시정조치 응답 시간 자체가 업계 표준 지표다** |
| `rework_requested` | 0/1 | |

**부수 효과 하나** — `incoming_defect_type`과 공장의 `defect_type`(§2.1)을 대조하면
**"이 공장이 합격시킨 걸 우리가 불합격시킨 비율" = 그 공장의 검사 신뢰도**가 공장별 계수로 나온다.
예측 피처이면서 동시에 협상 카드다.

### 5.4 출력은 업계 문법에 맞춘다

모델 출력을 **`예상 PPM`**(= 불량수/총수 × 1,000,000, 세계 수준 100 PPM 이하) +
**`로트 합격 확률`** 두 개로 내면 구매·품질 담당자가 설명 없이 알아본다.

## 6. T3 — CellOS/FactoryOS 설치 시 자동 수집

지금은 설치된 공장이 없으므로 **설계만 해두고 비워둔다.** 기존 `f4ge-quality-prediction`의
`process-telemetry.v1` · `cell-anomaly-signal.v1` 계약을 그대로 승계한다.

| 필드 | T2 어느 항목을 대체하나 |
| --- | --- |
| 설비 가동/정지 시각, 가동률 | `overtime_hours`, 수량 교차검증 |
| 사이클타임 | `produced_qty` 검증 |
| 이상탐지 이벤트 | `issue` 자기신고 대체 |
| 공구 교체 이력 | 치수 불량 원인 추정 |

**T3의 진짜 의미는 T1·T2의 자기신고 항목을 조작 불가능한 자동 관측으로 바꾸는 것이다.**
그래서 "CellOS를 깔면 리스크 점수가 좋아진다"가 아니라 **"CellOS를 깔면 점수를 신뢰할 수 있다"**가
영업 논리가 된다. 신뢰할 수 있는 공장에 더 좋은 조건을 줄 수 있으므로 공장에도 이익이다.
