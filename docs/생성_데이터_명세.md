## 1. 잠재변수 — 4계층으로 쌓는다

**불량은 관측값에서 나오지 않는다.** 잠재변수에서 나오고, 관측은 노이즈 낀 부분관측이다.
기존 프로젝트의 원칙을 그대로 승계한다.

### 계층 1 — 공장 상수 (12개, `factories.jsonl`)

| 잠재변수 | 분포 | 의미 |
| --- | --- | --- |
| `capability` | Normal(0, **1.0**) | log escape 스케일. 상하위 공장 약 10배 격차 ⚠가정 |
| `detection_rate` | Beta → 0.70 ~ 0.99 | **이 공장 검사가 내부 불량 중 몇 %를 잡나.** escape를 만드는 열쇠 |
| `report_bias` | 0.2 ~ 1.0 | 실제 불량률의 몇 배로 보고하나. 1.0 = 정직 ⚠가정 |
| `bias_sensitivity` | 0 ~ 1 | **나빠질수록 더 축소 보고하는 정도.** 모델의 핵심 상품이 여기 달렸다 ⚠가정 |
| `report_discipline` | 0.3 ~ 0.95 | 보고 지연·누락 성향 (MES 라도 API 가 끊긴다) |
| `factory_type` | a / b | **MES 연동 여부.** 3 / 9곳 (c 는 0 — 키만 남아 있다) |
| `has_mes` | bool | 유형 a. 자체 MES 가 FactoryOS 에 연동돼 생산·불량 정보가 오는가 |
| `has_cell` | bool | 전부 true — CellOS 는 협력 조건 |
| `mes_input_bias` | 0.55 ~ 1.0 | MES 입력 단계의 편향 — 폐기·재작업 판정은 사람이 한다 ⚠가정 |

⚠ ~~`t2_compliance`~~ · ~~`telemetry_installed`~~ 는 09-08 에 없어졌다.
**"사람이 얼마나 채우나"가 아니라 "시스템이 있나"** 로 바뀐 것이다.
`mes_input_bias` 는 `reports.py` 에서 불량 축소의 **하한**으로 쓴다(§2.3 식). 09-08 오후에 넣었다.

### 계층 2 — 제품군 (4개, `products.jsonl`)

| | 분포 |
| --- | --- |
| `difficulty` | Normal(0, 0.5) ⚠가정 |
| `nominal_cycle_sec`, `material_per_unit` | 고정값 |

### 계층 3 — 시점 상태 (공장 × 주)

| | |
| --- | --- |
| `state_t` | **AR(1), ρ = 0.3** ⚠가정. 부하율·인력 이탈·설비 노후의 합성 |

이 하나가 "공장이 나빠지고 있다"를 탐지할 수 있는지를 결정한다.
ρ가 0이면 과거가 미래를 못 말하고, 1에 가까우면 이력만으로 다 맞힌다.

### 계층 4 — 오더

| 잠재변수 | 만들어지는 법 |
| --- | --- |
| `schedule_pressure` | `lead_slack`(납기 여유)과 동시 진행 오더 수에서 유도. 음수면 무리한 일정 |
| `material_effect` | 자재 로트별. **공급사를 공유하는 공장끼리 같이 나빠진다** ← 공장 간 전파 경로 |
| `order_random` | i.i.d. 잔차 |

### 그리고 두 불량률이 여기서 갈린다

```
internal_defect_rate = sigmoid( base + capability + difficulty + state_t
                                + schedule_pressure + material_effect + order_random )
                       → 중앙값 0.03  (3~4시그마 실태)

escape_rate = internal_defect_rate × (1 − detection_rate)
                       → 중앙값 0.001 (≈ 1,000 PPM)
```

**`detection_rate` 가 escape 를 결정하는 두 번째 인자다.** 내부 불량률이 낮은 공장과
잘 걸러내는 공장이 다르고, 우리에게 도달하는 건 후자의 함수다.
그리고 이건 **"공장이 합격시킨 걸 우리가 불합격시킨 비율"로 관측된다.**

### 2.3 `factory_reports.jsonl` — L1, **일 1회** (~7,400행)

**오더 기간만큼 매일.** 편향·결측·지연이 전부 이 파일에서 발생한다.
⚠ **유형 a(MES 연동) 공장만 생성된다** — `has_mes` 가 아니면 빈 리스트다(`reports.py:73`).
결측은 사람의 누락이 아니라 **API 끊김**으로 해석한다.

**T1 (항상 시도, 그러나 누락 가능)**

| 필드 | 생성 방식 |
| --- | --- |
| `due_at` / `reported_at` / `delay_days` | 지연 = f(`report_discipline`, 상태 악화). **곤란하면 늦어진다** |
| `produced_qty` | 진척 곡선: 초기 setup 지연 → 정상 → 서두르면 후반 가속 |
| `scrap_qty` | 내부 불량 중 폐기분 (3~20%) |
| `rework_qty` | 나머지 — **분리해서 낸다.** scrap만 보면 문제의 3%만 보인다 |
| `stage` | setup / machining / finishing / inspection / packing |
| `promised_date_reported` | **매번 다시 낸다.** 값보다 변동 이력이 신호 |
| `issue_flag` | 실제 문제가 있어도 편향 때문에 "없음"이 나온다 |

**T2** — ~~`t2_compliance` 확률로 채워짐~~ → **유형 a 면 전부 온다.** MES 가 주는 값이다

| 필드 |
| --- |
| `inspected_qty`, `inspection_type`, `reject_qty`, `defect_type` |
| `material_lot_id`, `material_supplier`, `material_received_at`, **`material_consumed_qty`** |
| `machine_id`, `shift`, `operator_count`, `overtime_hours` |
| `photo_taken_at` (EXIF 시각) |

### ★ 보고 편향이 들어가는 지점

```
intent = report_bias
       × (1 − bias_sensitivity × 악화정도)      ← 나쁠수록 더 축소 (숨기려는 의도)
       × 노이즈
shrink = clip(intent, mes_input_bias, 2.0)      ← ★ MES 하한 (09-08). 재고가 안 맞으면 들통난다
rep_rework = true_rework × shrink                 ← 재작업이 가장 감추기 쉽다
rep_scrap  = true_scrap  × min(1, shrink + 0.35) ← 폐기는 감추기 어렵다
```

**노이즈가 아니라 편향이다.** 평균이 어긋난다. 그래야 불일치 탐지가 값을 한다.
**하한은 공장마다 다르다**(0.55~1.0). 사람이 쓰던 주간 보고에는 이 하한이 없었다(옛 값 0.02).
⚠ MES 공장 3곳 중 2곳에서 하한이 `report_bias` 보다 높아 **하한이 거의 항상 구속된다** —
실효 편향은 `max(report_bias, mes_input_bias)` 다. calibrate 구조 게이트도 이 값을 본다.

### ★ 교차검증 쌍이 성립하도록 생성한다

| 짝 | 생성 규칙 | 어긋나면 |
| --- | --- | --- |
| `produced_qty` ↔ `material_consumed_qty` | 자재 소진 = (양품+폐기+재작업) × 소요율. **실제값 기준으로 만든다** | 수량 부풀리기 |
| `reject_qty` ↔ `rework_qty`·`overtime_hours` | 재작업·잔업은 **실제 불량**을 따라간다 | 불량 은폐 |
| `promised_date_reported` ↔ `produced_qty` 추세 | 납기는 편향, 진척은 실제 | 낙관 보고 |
| `issue_flag` ↔ `delay_days` | 신고는 편향, 지연은 실제 | 문제 은폐 |
| `photo_taken_at` ↔ `reported_at` | 곤란하면 과거 사진 재사용 | 증거 재활용 |

**핵심**: 편향은 **자기신고 항목에만** 걸고, 물리적 소모량·시각은 실제값으로 둔다.
그래야 "한 지표를 좋게 만들면 다른 축이 어긋난다"가 데이터 안에서 성립한다.

## 3. 라벨 — `quality_outcomes.jsonl` (~900행)

| 필드 | 생성 방식 |
| --- | --- |
| `shipped_at` | |
| `arrived_at` | `shipped_at` + `market`별 운송일수 (18 / 30 / 60일) |
| `incoming_inspected_qty` | **ISO 2859-1 표본 크기** (`order_qty`에서 유도) |
| `incoming_reject_qty` | **Binomial(sample_n, escape_rate)** ← 여기가 y의 원천 |
| `lot_result` | accept / reject. 표본 200 · major면 10 이하 합격 |
| `defect_type_top` | 내부 불량 유형에서 유도 |
| `claim_occurred` … | 로트가 **합격해버린** 고 escape 오더에서 확률적으로 발생 |
| **`label_available_at`** | 도착 + 통관 + 검사. **학습 시 시간 커트라인이 된다** |

### ⚠ 구현하면서 발견 — 로트 합·불은 critical 이 정한다

처음 만들었을 때 **900 오더 중 로트 불합격이 0건**이었다. 버그가 아니라 설계 누락이었다.

```
표본 80개 × escape 600 PPM = 기대 불량 0.05개
major 2.5% 기준의 합격판정개수 = 5개
→ 수백 PPM 공급사는 major 기준으로는 사실상 절대 걸리지 않는다
```

실무에서 입고검사 불합격은 **critical(AQL 0, 하나만 나와도 불합격)** 에서 나온다.
그래서 불량마다 심각도를 붙이고 세 등급을 각각 판정한다.

| 등급 | AQL | 표본 80에서 합격판정 |
| --- | --- | --- |
| critical | 0 | **0개** — 하나만 나와도 불합격 |
| major | 2.5% | 5개 |
| minor | 4.0% | 7개 |

이 하나로 로트 불합격률이 **0% → 2.6%** 가 되어 실무 범위(1~10%)에 들어왔다.
⚠ 심각도 구성(critical 0.25 / major 0.50 / minor 0.25)은 **실측 근거가 없는 다섯 번째 가정**이다.

**y가 두 층이다:**

| | 정의 | 성질 |
| --- | --- | --- |
| `y_rate` | `reject_qty / inspected_qty` | **Beta-Binomial로 모델링.** 표본 크기가 가중치 |
| `y_lot` | accept / reject | 희소. 보조 지표 |

> 표본 200 × escape 0.1% = **기대 불량 0.2개.** 대부분의 오더에서 0이 나온다.
> 이래서 단순 비율이 아니라 Beta-Binomial 이어야 한다 — 0을 봐도 사후분포가 움직인다.

## 4. `ground_truth.jsonl` — 모델이 절대 못 보는 것

| 필드 |
| --- |
| `internal_defect_rate_true`, `escape_rate_true`, `true_defect_count` |
| `state_t`, `schedule_pressure`, `material_effect` |
| `reported_vs_true_gap` — **불일치의 정답값** |

**왜 필요한가**: "모델이 예측을 얼마나 맞혔나"와 별개로
**"모델이 진짜 상태를 얼마나 복원했나"**를 잴 수 있다.
특히 불일치 탐지는 **정답이 있어야만 평가된다** — 실데이터에서는 영원히 알 수 없는 값이라,
합성 단계에서 재두지 않으면 이 기능의 성능을 한 번도 측정 못 한다.

## 5. 시간 구조

```
36개월 · 오더 900건 · 공장 12곳
  ├─ 오더 발생: 월 25건, 공장별 부하에 따라 배분

  └─ 라벨 도착: 출하 + 18~60일 + 통관·검사

분할: 시간순 60 / 20 / 20 (무작위 분할 금지 — 기존 프로젝트에서
      무작위 분할이 ROC-AUC 를 0.558 → 0.71~0.80 으로 부풀린 사례 확인)
```

**`label_available_at`을 반드시 지킨다.** t 시점에 학습할 때
그 시점까지 **도착한** 라벨만 쓴다. 이걸 안 지키면 유럽 오더(60일)에서
실제로는 불가능한 학습을 하게 된다.

## 6. ⚠ 규모 문제 — 현실 규모로는 평가가 안 된다

| | 오더 | 로트 불합격(5%) | 시간순 test 20% | test 양성 |
| --- | --- | --- | --- | --- |
| **현실 규모** (18개월) | 450 | 22건 | 90 | **4~5건** |
| **생성 규모** (36개월) | 900 | 45건 | 180 | **9건** |

**900건으로도 이진 평가는 신뢰구간이 너무 넓다.** 그래서:

1. **주 평가지표는 `y_rate` 기반**(Beta-Binomial log loss · 예상 PPM 보정도).
   불합격 건수보다 정보량이 훨씬 크다
2. **`y_lot`은 보조 지표**로만 보고, 신뢰구간을 반드시 같이 낸다
3. **seed 최소 5개.** 기존 프로젝트에서 1 seed 결론이 3 seed 재측정에 뒤집힌 전례가 있다
4. 그리고 **데이터량 곡선**을 그린다 — 450건(현실) / 900 / 1,800에서 성능이 어떻게 변하나.
   "몇 년 치가 쌓여야 쓸만해지는가"가 그 자체로 영업 답변이 된다

## 8. 만드는 순서

```
1. factories · products 마스터        → 잠재값 고정
2. 오더 스케줄 36개월                  → 공장 부하·자재 로트 배정
3. 오더별 잠재값 → 두 불량률           → ground_truth.jsonl
4. MES 일 집계 생성 (편향·지연·결측)    → factory_reports.jsonl  (유형 a 만)
5. FAI 생성                            → fai_reports.jsonl
6. AQL 표본 → 라벨 + 지연              → quality_outcomes.jsonl
7. 우리 쪽 메타 집계                   → order_meta.jsonl
8. 검증 게이트 통과 확인
```

3번이 끝나야 4번이 가능하다 — **보고는 진실의 함수**이기 때문이다.
